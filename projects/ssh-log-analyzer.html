SSH Log Analyzer

A command-line tool that reads a Linux server's login log and flags the attacks a security analyst would want to see first, using nothing but Python's standard library.

The problem

Any server reachable from the internet gets login attempts within minutes of going online. The evidence lands in /var/log/auth.log as thousands of near-identical lines. Reading it by eye doesn't scale, and the one line that matters, a successful login after a run of failures, is easy to miss.

What I built

A tool that turns the raw log into a short, ranked list of findings:

  • SUCCESS_AFTER_FAIL (HIGH): an IP failed several times, then got in. Possibly a guessed password.
  • BRUTE_FORCE (MEDIUM): five or more failures from one IP inside a ten-minute window.
  • PASSWORD_SPRAY (MEDIUM): one IP trying many different usernames. Sprays are often slow on purpose, so this rule ignores timing.

It writes a text or JSON report, every threshold is adjustable from the command line, and exit codes make it usable from scripts and scheduled tasks.

Key decisions

  1. Treat the log as hostile input. Attackers choose the username. A naive parser can be tricked by a username like x from 10.0.0.5 port 22 ssh2 into blaming an innocent IP. The pattern anchors to the end of the line, where sshd always writes the real address, and a test proves it.
  2. A sliding window for rate detection. The brute-force rule walks each IP's failures in time order and slides the window forward, reporting the peak burst rather than a lifetime total that would flag slow, harmless typos.
  3. Every rule has a near-miss test. Four failures don't trip a threshold of five; one typo before a login is normal. A rule that cries wolf gets ignored, so false alarms are tested as carefully as detections.
  4. Fail clearly. Missing files, unreadable files, and undecodable bytes (attackers send garbage) all produce one-line errors and exit code 2, never a stack trace.

What's next

  • Support the ISO timestamps newer Ubuntu releases write.
  • Add a time limit to the break-in rule, so three typos a month apart don't count.
  • Pull logs straight from AWS CloudWatch with boto3, linking it to the S3 auditor.
