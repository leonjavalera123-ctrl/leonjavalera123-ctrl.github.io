S3 Security Auditor

A read-only command-line tool that checks every S3 bucket in an AWS account for the misconfigurations behind real data leaks, and tells you how to fix each one.

The problem

Most cloud data leaks aren't clever hacks. They're a storage bucket someone made public by accident: a policy that grants "Principal": "*", or an old access-control list nobody remembers. AWS has added guardrails over the years, but older buckets and one-off changes slip through.

I wanted a tool that answers one question for a whole account in a few seconds: which buckets could leak, and what exactly should I change?

What I built

A Python CLI that reads each bucket's settings and runs nine checks, modeled on AWS's own security best practices:

  • HIGH: public bucket policies, and ACLs that grant access to everyone or to any AWS account.
  • MEDIUM: Block Public Access not fully on (account or bucket), no rule rejecting plain-HTTP requests, no default encryption.
  • LOW: versioning off, access logging off, legacy ACLs still enabled.

Every finding includes a one-line fix. Output is a readable report or JSON, and the exit code (0 clean, 1 findings, 2 error) lets a script or CI pipeline act on the result.

Key decisions

  1. Model how settings interact, not just each setting. A public policy that Block Public Access is overriding is reported as LOW, not HIGH: safe today, one click from exposed. Public ACLs don't count when ACLs are disabled. Simple checkers get these wrong in both directions.
  2. Never guess. If AWS refuses to show a setting (AccessDenied), that check is listed under "Couldn't check" instead of being counted as a pass. A silent pass is the most dangerous output an audit tool can produce.
  3. One file talks to AWS. collector.py turns API responses into plain Python objects; the rules in checks.py never call AWS. That makes the security logic testable without an account and easy to read.
  4. Least privilege by default. The README ships the exact IAM policy the tool needs (ten Get/List actions) and recommends short-lived SSO credentials, so no access keys ever sit in the project folder.
  5. A demo that needs no AWS account. --demo builds a simulated company account with moto, five buckets from fully hardened to wide open, so anyone can run it in seconds.

A bug worth telling

The demo crashed inside moto, the library that simulates AWS. Its fake logging feature assumed every policy principal was a dictionary, so the common shorthand "Principal": "*" broke it. AWS treats {"AWS": "*"} as identical, so I used the long form for that one bucket and left a comment explaining why, rather than weakening the real checks.
