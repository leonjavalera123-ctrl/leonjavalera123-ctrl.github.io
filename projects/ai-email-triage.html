AI Email Triage Toolkit

Step one of an AI email-assistant business, and deliberately not the assistant itself. A toolkit that measures whether a small local model can sort mail well enough to trust, before a line of assistant code is written.

The problem

Small businesses drown in email, and an AI assistant that sorts it sounds easy to build. The hard part is knowing whether it works. If you build the assistant first, you can't tell whether changing a prompt made it better or just different.

So the first question had to be: can a small model running on this machine tell mail that needs the owner from mail that doesn't, well enough to trust?

What I built

An evaluation toolkit that turns a real mailbox into an honest test. Nothing in it calls a language model until the final bake-off, and all mail stays on the local machine.

Every email gets one of four labels: ESCALATE (the owner needs this, soon), DRAFT (a reply an assistant could write), FILE (a real person, no reply needed), or BULK (newsletters and notifications).

Key decisions

  1. Accuracy is the wrong number. Most of an inbox is newsletters, so a model that answers "routine" to everything scores about 90% and catches zero emergencies. The toolkit optimizes for miss rate on the mail that mattered.
  2. Stratified sampling. A random sample of 200 emails is mostly newsletters. Splitting the inbox into categories and sampling each equally means rare, important mail is properly represented.
  3. Test the labeller, not just the model. Everything gets labelled twice, blind, and agreement is measured with Cohen's kappa. If I can't apply my own definition of ESCALATE consistently, no model can learn it.
  4. A locked test set. Data is split into a development set and a held-out test set, guarded by an explicit --yes-really-spend-test flag, so any accuracy number quoted to a client is honest, not tuned.
  5. Private by design. It processes real email, so the code stays private and nothing leaves the machine. Models run locally through Ollama.

The workflow

one step per commandpython -m evalset ingest mail.mbox --me owner@...   # import locally
python -m evalset sample                           # stratified sample
python -m evalset label --pass 1                   # labelling UI on localhost
python -m evalset label --pass 2                   # label again, blind
python -m evalset agreement                        # Cohen's kappa: go / no-go
python -m evalset control                          # did the bulk filter hide real mail?
python -m evalset split                            # dev / held-out test
python -m evalset bakeoff                          # score local models on dev

What's next

  • Label a full sample and clear the agreement bar.
  • Run the model bake-off, then decide whether a local model is good enough or a larger one is needed.
  • Only then build the assistant, with the evaluation set as its regression test.
